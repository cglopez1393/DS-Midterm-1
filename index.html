Concurrency

Multiple components execute at the same time and may share resources.

Raft in one sentence

A single-leader consensus algorithm designed to keep replicated logs consistent in the presence of ordinary node/network failures.

Follower
timeout →
Candidate

Leader

Election flow — say this in order

  1. Followers expect heartbeats from the leader.
  2. A follower's randomized election timeout expires.
  3. It becomes candidate, begins a new election/term, votes for itself and requests votes.
  4. It needs a majority of configured nodes. 5 nodes → 3.
  5. Winner becomes leader and sends heartbeats/AppendEntries; followers reset election timers.
Course slide wording says the next candidate is “selected at random.” The more precise Raft mechanism is randomized election timeouts; there is no central random selector.

Lab 1 visual lesson: receiving an entry is not the same as learning it is committed. The leader first establishes majority support; later communication lets followers learn the commit.

If one follower is stopped, it misses entries. When it returns, Raft catches it up. If only 2/5 nodes remain, there is no majority, so new entries cannot become committed under the simplified lab scenario.

Raft handles

Leader crash, follower crash, partitions/network failure, log replication and leader election.

Raft does NOT solve by itself

Byzantine/malicious behavior or MITM message alteration. Use cryptographic authentication/signatures for integrity/authenticity.

Limitations from Lab 1

Single leader can bottleneck; not Byzantine fault tolerant; leader election includes log-freshness restrictions.

Nakamoto consensus — six steps

  1. New transactions are broadcast.
  2. Each node/miner collects transactions into a candidate block.
  3. Miners search for a difficult Proof of Work (nonce).
  4. A miner finding valid PoW broadcasts its block.
  5. Other nodes accept only if transactions are valid/not already spent and PoW is valid.
  6. Nodes express acceptance by mining the next block using the accepted block's hash as previous hash.

Proof of Work memory formula

Each hex digit has 16 possibilities. Probability of 00 = 1/16² = 1/256, so expected attempts = 256. For 000: 16³ = 4096.

Expected hashes = 16 ^ (# required leading hex zeros)
Total hash rate = miners × hashes/sec per miner
Expected seconds = expected hashes / total hash rate
Course example: three zeros, 35 peers at 1 hash/sec → 4096 / 35 ≈ 117 seconds.

Two valid blocks at nearly the same time create a temporary fork. Miners may build on the valid block they heard first. Subsequent PoW extends one branch; the network converges on the branch with more accumulated work (course often simplifies this as the “longer valid chain”).

Miners / digital currency

Miners listen for transactions, verify signatures and no double spending, validate received blocks/nonce, assemble candidate blocks, search for a nonce, publish blocks, and are incentivized by block rewards/fees. PoW makes a Sybil attack expensive because influence is tied to computation rather than simply creating identities.

Each layer provides an abstraction: HTTP request/reply → reliable TCP stream or UDP datagram → IP datagram across internetwork → local-link frame.

Addressing by layer

Transport: port number (16-bit, 0–65535) identifies software delivery endpoint/process mapping.

Internet: IP address identifies host/interface for routing across networks.

Link: MAC address identifies local-link interface.

Apartment memory: IP = building address; port = apartment/room; MAC = local delivery label on the current link.

TCP vs UDP

TCP

Connection-oriented, reliable, ordered stream, acknowledgements/retransmission, flow control.

UDP

Connectionless datagrams, low overhead, no built-in reliability/order/ACK; app can add reliability if needed.

Not interoperable: a TCP endpoint does not directly communicate with a UDP endpoint as though they were the same transport.

IPv4 + subnetting

IPv4 address = 32 bits. Subnet mask marks network bits (1s) vs host bits (0s).

Network address = IP address BITWISE AND subnet mask

Exam goals from lecture: given IP + mask, find network address, host number/portion, and determine whether two addresses are on the same network.

Quick /24: 192.168.7.34 /24 → network 192.168.7.0; host portion = 34. Two /24 addresses are same network if first three octets match.

DHCP / DNS / ARP

DNS: NAME → IP

ARP: local IP → MAC

DHCP: gives IP + subnet mask + gateway + DNS + lease

ARP process: check cache → if missing, broadcast ARP request on local network → matching host replies with MAC → cache mapping.

Router vs switch

Router: IP/internet-layer forwarding between networks using routing tables.

Switch: local-link forwarding associated with MAC addresses inside a LAN.

If destination is on another network, host sends local frame toward the default gateway's MAC while the IP destination still identifies the remote destination.

Routing algorithms

RIP: simple distance-vector interior gateway protocol; routers exchange routing information with neighbors.

Link-state: routers distribute link-state information, maintain a network map/database, and compute shortest paths (Dijkstra).

BGP: exterior routing between large organizations/ISPs; policy matters.

1. What a distributed system is

Course definition: a distributed system has components on networked computers that communicate and coordinate their actions only by passing messages.

Concurrency

Different components execute at the same time. They can act on shared resources concurrently, which creates coordination problems.

No global clock

There is no perfectly shared time source that every node can use to order all events exactly.

Independent failures

One machine, process, network link, or service may fail while the rest keep running. This is a defining distributed-systems difficulty.

Exam translation: if a question asks why a web app, Raft cluster, blockchain network, or API composition is “distributed,” look for multiple components, network communication, concurrency, and partial failure.

Memory: Different places + messages + imperfect timing + partial failure.

2. Message-passing patterns

Fire-and-forget

Sender transmits without waiting for confirmation. UDP is the course's main transport example. Fast/simple, but the sender cannot assume delivery.

Request/response

Client sends a request and waits for the server response. HTTP is the main course example.

Request/acknowledge

Sender receives confirmation that a message/action was received or processed. Reliability logic often depends on acknowledgements.

Persistent/streaming

Communication may remain active rather than existing only for one transient request. Your notes contrast this with request-bound communication.

HTTP coupling from the lecture: client and server are coupled in time (both must participate during the interaction) and space (the communicating endpoints need addressing information).

7. Safe and idempotent HTTP methods

Safe: intended not to change server/application state. Idempotent: repeated identical requests have the same intended final effect as one.

MethodTypical purposeSafe?Idempotent?Why
GETRetrieveYesYesRead operation should not intentionally change state.
HEADRetrieve headers onlyYesYesMetadata read.
PUTInsert/replace a resource at a known identifierNoYesChanges state, but repeating the same replacement yields same final intended state.
DELETERemove resourceNoYesAfter deletion, repeated delete still leaves it deleted.
POSTCreate/add/actionNoNo, generallyRepeating may create multiple records/actions.

Failure connection: idempotence is useful when a response is lost. The client may not know whether the server performed the action; retrying an idempotent request does not intentionally create a different final state.

🧭 Raft, Blockchain & Nakamoto — Deep Dive

Raft from zero

Raft is a consensus protocol aimed at keeping replicated state/logs consistent despite node/network failures. The course emphasizes a single leader.

Client request
→
Leader
AppendEntries
Followers replicate
acks
Leader learns majority
commit
Followers learn commit

Only the leader accepts/appends normal new client entries. Followers replicate leader entries. Candidates exist during election.

Election sequence

  1. Followers expect leader heartbeats.
  2. A follower's randomized election timeout expires.
  3. It becomes candidate, starts new election term, votes for itself.
  4. Candidate requests votes.
  5. A majority elects the candidate leader.
  6. Leader begins sending heartbeats/AppendEntries.

Five-node majority: 3. Seven-node majority: 4. Formula: floor(N/2)+1.

What if no majority?

Without a reachable majority, the cluster cannot safely commit new writes under Raft's majority rule. A current leader may still have uncommitted/tentative log entries; if leadership changes, uncommitted entries are not guaranteed to survive.

What Raft does not solve

The blockchain/Raft lecture explicitly states Raft does not address a man-in-the-middle attacker changing messages. Raft assumes non-Byzantine participants for its normal safety model. Authentication/signatures are separate security mechanisms.

Nakamoto consensus six-step core

  1. New transactions are broadcast to nodes.
  2. Nodes/miners collect transactions into candidate blocks.
  3. They search for difficult proof-of-work.
  4. Winner broadcasts the block.
  5. Nodes accept it only if transactions and PoW are valid.
  6. Acceptance is expressed by mining the next block using accepted block's hash as previous hash.

Proof-of-work math

If the requirement is k leading hexadecimal zeros, each hex digit has 16 possibilities, so:

Probability per hash = 1 / 16^k
Expected hashes      = 16^k
Expected time        = 16^k / total network hash rate

Example: difficulty 2 → 16² = 256 expected hashes. Difficulty 3 → 4096. If 35 miners do 1 hash/sec each, 4096/35 ≈ 117 sec — this exact style appears in the lecture.

Bitcoin miner duties

Listen for transactions; validate signatures/no double spending; maintain blockchain; validate received blocks and PoW; build candidate block extending current best/longest-valid-chain view; find nonce; publish; receive incentives such as block reward/transaction fees in course discussion.

Forks

If two valid blocks arrive around the same time, a temporary fork exists. Course material says miners initially may build on the one heard first; when another block extends one branch, the fork resolves as the network converges on the branch with the greater chain/work criterion used by the course.

🔐 Security Add-on Recent quiz/conversation topics

Scope note: These points were in your recent quiz questions, but a dedicated security lecture file was not among the uploaded test-source PDFs used for the main app. Keep this section separate from the course-source-grounded sections above.

Digital certificate

A digital certificate binds an identity to a public key using a trusted issuer's signature. In quiz wording, its role is to help verify authenticity/identity rather than prove that nobody listened or that an encryption algorithm is mathematically secure.

RSA

RSA security relies on the computational difficulty of factoring a large integer that is the product of large primes. Large keys and computational cost are consequences/parameters; the core mathematical hardness assumption is factoring.

Replay attack

An attacker re-sends a previously valid message. The danger is that a receiver may treat the old message as a new valid action. Nonces, timestamps, sequence numbers, or challenge-response designs can help detect replay.

Worst key failure

If a decryption/private/secret key is exposed, the cryptographic protection can be defeated even if the algorithm itself is strong. Modern cryptography assumes algorithms may be public; secrecy belongs in the keys.

Secret-key cryptography

Another name is symmetric cryptography: the same shared secret (or closely related secret material) is used for encryption/decryption. Public-key cryptography is asymmetric.

    BufferedReader in = new BufferedReader(
        new InputStreamReader(client.getInputStream()));
    PrintWriter out = new PrintWriter(client.getOutputStream());

    String firstLine = in.readLine();            // e.g. GET /hello HTTP/1.1
    out.println("HTTP/1.1 200 OK");
    out.println("Content-Type: text/plain");
    out.println();                               // blank line: headers/body split
    out.println("hello");
    out.flush();
    client.close();
}

How to trace it: listen → accept → read → interpret → write status/headers/body → flush → close.

7. TCP vs UDP — phone call vs postcard

TCP = phone call

Connection first; reliable ordered stream; acknowledgements/retransmission. Good when complete, ordered data matters.

UDP = postcard

Send a datagram and move on; no built-in guarantee it arrives or arrives in order. Application can add reliability if needed.

Do not overuse the analogy: on the exam, use the course terms “connection-oriented reliable stream” for TCP and “datagram / no built-in reliability guarantee” for UDP.

8. DNS, ARP, DHCP — three questions

Ask yourself:

"I know a NAME. What IP is it?"       → DNS
"I know a local IP. What MAC?"        → ARP
"I just joined the network. What settings do I use?" → DHCP

Memory chain for opening a site: name can be resolved by DNS → IP routing gets toward the destination → on a local link ARP may be needed to learn the next-hop MAC.

9. Subnet example — use AND logic

Made-up example: IP 192.168.10.77, mask 255.255.255.0 (/24).

IP:      192.168.10.77
Mask:    255.255.255.0
AND →    192.168.10.0   ← network address
Host:                 77

Another IP 192.168.10.200 with the same /24 also has network 192.168.10.0, so they are on the same subnet. 192.168.11.20/24 is a different network.

10. Raft election — classroom analogy

Five students need one spokesperson. Everyone starts as a follower. If student C waits too long without hearing the current spokesperson, C becomes a candidate, votes for itself, asks others, and needs 3 of 5 total votes. Once elected, C keeps sending “I am still leader” heartbeat messages.

Important correction: the analogy is only for memory. On the exam say randomized election timeout, candidate, RequestVote, majority, leader, heartbeat/AppendEntries.

11. Raft replication — why majority matters

5 nodes: A B C D E
Entry X stored on: A B C
That is 3/5 → majority

If A later fails, B and C still have X, and Raft's election/log rules are designed to preserve committed history. If only A and B have a new entry (2/5), it is not committed in the simplified course model.

12. Nakamoto PoW — raffle-ticket analogy

Each hash attempt is like buying a raffle ticket whose result you cannot predict. If the rule is “hash starts with 000,” one exact 3-hex-digit prefix occurs with probability:

1 / 16³ = 1 / 4096
Expected attempts ≈ 4096

If 20 miners each do 2 hashes/sec, total rate = 40 hashes/sec, so expected time ≈ 4096 / 40 = 102.4 sec.

Scraping

Download HTML meant for a browser, then search/parse it to extract a value. Fragile if page structure changes.

API

Quick Look written practice exam

1. (5 pts) Raft election: In a 5-node cluster the leader dies. Explain the sequence from missed heartbeat to a new leader and what happens after election.
Model answer: A follower's randomized election timeout expires, so it becomes a candidate, starts a new term/election, votes for itself and requests votes. A majority (3/5) elects a leader. The new leader sends heartbeats/AppendEntries so followers remain followers and reset election timers.
2. (5 pts) Raft replication: A command is on A, B and C in a 5-node cluster. D and E do not have it. Explain majority, commitment in the simplified course model, and why majority matters if A crashes.
Model answer: A+B+C is 3/5, a majority. Under the simplified course model A need not wait for D/E. Majority replication supports commitment and protects committed history across leader failure because a new leader is selected using Raft log/election safety rules.
3. (4 pts) Security: A MITM changes 'Store 8' to 'Store 9'. Is Raft the primary solution? Explain and name a suitable security mechanism.
Model answer: No. Raft is primarily a consensus/failure-tolerance protocol for node/network failures, not malicious alteration. Authentication/digital signatures can detect unauthorized modification and sender impersonation.
4. (5 pts) PoW: difficulty requires 000; 20 miners each do 2 hashes/sec. Show expected hashes, total hash rate, and expected time.
Model answer: Expected hashes = 16^3 = 4096. Network rate = 20×2 = 40 hashes/sec. Expected time = 4096/40 = 102.4 seconds.
5. (4 pts) Nakamoto fork: Two valid blocks extend the same parent at nearly the same time. Explain what miners do immediately and how the network later converges.
Model answer: This is a temporary fork. Different miners may build on the valid block they heard first. When subsequent blocks extend one branch, that branch accumulates more proof of work and miners converge on it; the other branch becomes stale/orphaned in simplified course wording.
6. (6 pts) HTTP: Give safe/idempotent classifications for GET, POST, PUT, DELETE and explain why idempotence matters after a lost response.
Model answer: GET safe+idempotent; POST not safe+not generally idempotent; PUT not safe+idempotent; DELETE not safe+idempotent. Idempotence matters because if the response is lost, retrying an identical operation can preserve the same intended final state.
7. (5 pts) Servlet/JSP trace: Explain browser → HTTP → web container → servlet → model → setAttribute → RequestDispatcher.forward → JSP → response browser flow.
Model answer: The browser submits an HTTP request. The web server/container routes URL+verb to the servlet. The servlet/controller reads parameters and calls the model. The model performs the data work and returns a result. The controller sets request attributes and forwards internally to a JSP. The JSP executes server-side and generates HTML, which is returned in the HTTP response and rendered by the browser.
8. (4 pts) Lab 4: Explain ServerSocket, accept(), the connected Socket, input/output streams, and why the simple server returns 200 or 404.
Model answer: ServerSocket listens on the server port. accept() blocks until a client connects, then returns a connected Socket. The server reads HTTP from the socket input stream and writes the HTTP response to the output stream. Existing file → 200 OK; missing file/FileNotFoundException → 404 Not Found.
9. (4 pts) Networking: Explain DNS, DHCP and ARP without reversing any direction.
Model answer: DNS resolves domain NAME→IP. DHCP gives a host network configuration such as IP, subnet mask, default gateway and DNS server. ARP resolves a known local IPv4 address→MAC address on the local link.
10. (4 pts) Docker: Explain image vs container, ROOT.war, and -p 9000:8080.
Model answer: An image is the packaged template built from Dockerfile/app. A container is the running isolated process created from it. ROOT.war deploys the web app as Tomcat's root context. -p 9000:8080 maps host port 9000 to container port 8080.
11. (4 pts) Project 1 Task 3: Compare scraping and APIs/JSON and explain MVC separation.
Model answer: Scraping fetches human-oriented HTML and extracts data from it. An API returns structured data such as JSON, which GSON parses in Java. The servlet/controller coordinates, the model handles remote/data logic, and the JSP/view presents results.
12. (4 pts) Project 1 Task 2: Why is GET /getResults that also clears results a bad HTTP design, and how would you redesign it?
Model answer: GET is supposed to be safe, but clearing results changes application state. Keep GET /getResults read-only and use a separate state-changing request such as POST /clearResults.
